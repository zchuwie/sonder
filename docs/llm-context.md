## What Sonder Is

Sonder is a place-based anonymous content platform. Users pin thoughts, photos, and songs to real-world locations on an interactive map. An admin panel handles moderation, reporting, and audit history.

- **Web app** (`apps/web`, port 3000): Public-facing map + post creation
- **Admin app** (`apps/admin`, port 3002): Moderation dashboard
- **Monorepo**: pnpm workspaces + Turborepo

## Authentication Model

Sonder uses **Supabase Anonymous Auth** exclusively for the public web app:

1. First visit: `signInAnonymously()` creates a permanent user record in `auth.users` with `is_anonymous = true`
2. A session is stored in browser cookies (managed by `@supabase/ssr`)
3. The session consists of:
   - **Access token** (JWT): expires after 1 hour, auto-refreshed by Supabase client
   - **Refresh token**: long-lived (persists in httpOnly cookie), used to generate new access tokens
   - **User ID** (UUID): permanent, never changes, stored in `auth.users`
4. The user ID links posts (`created_by`), uploads, reports, and rate-limit keys to that anonymous session
5. If cookies are cleared or a new device is used, a new anonymous user is created
6. Old posts remain in the database under the old user ID — orphaned but still exist

**Admin app** uses email/password auth with an `admin_users` table check.

**Why anonymous auth:**
- Enables RLS (Row Level Security) policies that reference `auth.uid()`
- Allows per-user rate limiting
- Tracks who uploaded what image
- Lets users see their own pending posts
- No registration friction for users

## Database Schema

### Tables

**posts**
- `id` uuid PK
- `title` text (1-50 chars)
- `body` text (1-1000 chars)
- `lat` double, `lng` double
- `place_name` text (optional)
- `group_key` text (for location grouping)
- `image_path` text (references Storage path, nullable)
- `music` jsonb (title, artist, providerId, previewUrl, coverUrl, etc.)
- `status` enum: pending | approved | rejected | flagged | archived
- `created_by` uuid → auth.users
- `deleted_at` timestamptz (soft delete)
- `delete_reason` text
- `status_updated_at` timestamptz (set by trigger)
- `moderation_reason` text
- `created_at`, `updated_at`

**post_reports**
- `id` uuid PK
- `post_id` → posts
- `reason` text (1-120 chars)
- `details` text (optional, up to 1000)
- `reported_by` uuid → auth.users
- `status` enum: open | reviewing | resolved | dismissed | actioned
- Unique: `(post_id, reported_by)` — one report per user per post

**moderation_events** (audit log)
- `id` uuid PK
- `post_id` → posts (nullable)
- `action` text (submitted, approved, rejected, archived, deleted, restored, report_dismissed, report_resolved)
- `reason` text
- `actor_id` uuid → auth.users
- `created_at`
- Auto-populated by triggers on `posts` status/deleted_at changes and `post_reports` status changes

**music_cache**
- Deezer track metadata cache (provider_id, title, artist, album, cover_url, preview_url, duration)

**admin_users**
- `user_id` uuid PK → auth.users
- `email`, `role`, `created_at`

**heartbeats** (active user tracking)
- `user_id` uuid PK → auth.users
- `last_seen` timestamptz
- Active users = rows where last_seen > now() - 2 minutes

### Storage

- **Bucket:** `post-images` (private, 5 MiB limit, jpeg/png/webp only)
- Users upload to `{userId}/{uuid}.{ext}` (RLS enforced)
- Public access via signed URLs generated by `signed-post-image` edge function (10 min expiry, cached 5 min in-memory)

## Edge Functions (Supabase/Deno)

| Function | JWT Required | Purpose |
|----------|-------------|---------|
| `create-post` | Yes | Validates input, rate-limits, inserts post + logs event |
| `signed-post-image` | No | Returns signed URL for a post's image |
| `deezer-search` | No | Proxies Deezer music search |

**Rate limiting:** Uses Upstash Redis. Per-user (5 posts/10min) and per-IP (20 posts/hr). Bypassed when `IS_DEVELOPMENT=true`.

**Shared utilities** (`_shared/`): CORS, rate limiting, IP hashing (SHA-256 with salt), input validation, Supabase client factories.

## Post Creation Flow

1. User opens `/map` → clicks "Create a post" (desktop navbar) or holds to pin (mobile)
2. `NavCreatePostModal` opens (desktop) or `CreatePostModal` opens (mobile via pin)
3. User picks location (search or map click), fills title + body, optionally adds photo + song
4. On submit:
   - If image: uploads directly to Supabase Storage (`post-images/{userId}/{uuid}.ext`)
   - Calls `create-post` edge function with title, body, lat, lng, placeName, imagePath, music
   - Edge function validates, rate-limits, inserts into `posts` table, logs `submitted` event
5. Post appears as `status: pending` — invisible on public map until admin approves
6. Toast notification confirms submission

---

## Admin Moderation Flow

1. Admin logs in with email/password → `requireAdmin()` checks `admin_users` table
2. Dashboard shows: active users (heartbeat), pending count, approved count, reports, audit log
3. Pending posts queue: admin can approve/reject with optional reason
4. Approved posts: admin can archive or soft-delete
5. Reports: admin can dismiss (restores post if flagged), mark reviewing, or action (archive post)
6. All actions auto-logged to `moderation_events` via database triggers
7. Realtime updates via Supabase Postgres Changes (admin subscribes to posts, post_reports, moderation_events)

## Activity Polling (Web)

- `useActivityPulse` hook polls `/api/activity` every 60 seconds
- Sends heartbeat POST (updates `heartbeats` table)
- Compares post count — if increased, shows fun toast ("Someone just dropped a thought 💭")
- Calls `refreshPosts()` to update map markers with new approved posts
- Pauses when tab is hidden (`document.hidden`)

## Security Model

| Layer | Protection |
|-------|-----------|
| Database | RLS on all tables. Public can only read approved/flagged posts. Writes go through edge functions. |
| Admin | Server-side `requireAdmin()` checks `admin_users` table. RLS uses `is_admin()` function. |
| Rate limiting | Edge functions enforce per-user and per-IP limits via Upstash Redis. |
| Input validation | All user input validated and length-capped in edge functions. |
| Storage | Per-user folder isolation via RLS. Private bucket, signed URLs for access. |
| IP privacy | IP addresses hashed with salt (never stored raw). |
| CORS | Currently `*` (should be restricted before launch). |
| Cookies | Supabase SSR manages httpOnly auth cookies. |

### Known Security Issues (pre-launch)

1. **CRITICAL:** `imagePath` in `create-post` not validated against user ID — path traversal possible
2. **HIGH:** CORS is `Access-Control-Allow-Origin: *` on all edge functions
3. **HIGH:** No Next.js middleware file → sessions don't auto-refresh server-side
4. **HIGH:** In-memory session cache doesn't check token expiry
5. **MEDIUM:** `IS_DEVELOPMENT=true` must be set to `false` in production secrets

## Caching Strategy

| What | Where | TTL |
|------|-------|-----|
| Signed image URLs | In-memory Map (both apps) | 5 min |

## Design Decisions

1. **Anonymous auth over no auth:** Enables RLS, rate limiting, upload isolation, and post ownership without user registration
2. **Edge functions over direct DB writes:** Centralized validation, rate limiting, and audit logging
3. **Polling over Realtime for web:** Cheaper, simpler, sufficient for "someone posted" notifications
4. **Realtime for admin:** Low connection count, high value (coordination between admins)
5. **Soft delete over hard delete:** Posts with `deleted_at` stay in DB for audit/export but invisible everywhere
6. **Signed URLs over public bucket:** Images are private until post is approved
7. **In-memory image URL cache:** Avoids re-fetching signed URLs on every render (5 min TTL)
